# 2026-11-24 compose 项目名冲突事故

> 读者：维护者

状态：已修复，写成后不再修改。对应版本：0.4.0 发现，0.4.1 修复。

## 经过

在一台正在提供服务的服务器上测试时，测试实例的服务器用户用了默认名 `owner`。docker compose 默认用目录名作项目名，于是测试实例的 `users/owner` 和真实部署的 `users/owner` 被当成同一个项目，`up -d` 把真实的 `rcc-owner` 重建成了测试配置（挂载测试数据、接入测试网络）。持续约 2 分钟，期间没有用户连接，真实数据目录没有被写入，随后已恢复。

同一类问题在正式使用中也可能出现：服务器用户名和宿主机上已有的 compose 项目同名（比如 `kavita`）时，删除用户时的 `--remove-orphans` 可能删掉别人的容器。

## 修复

- 每个用户容器显式使用项目名 `rcc-<用户名>`，网关使用实例的网络名。
- 新增归属检查：同名容器属于别的部署目录，或者不是 remote-cc 创建的，一律拒绝。
- 所有地方都不再使用 `--remove-orphans`；补发邀请码不再改动容器。
- 老部署在下一次更新服务器时迁移项目名，这一步本来就会先检查活跃会话。

回归测试：在测试实例里创建 `owner` 被拒绝，真实容器的创建时间不变；创建和删除名为 `kavita` 的用户，不影响真正的 kavita 容器。

## 后续

端到端测试从这台服务器移到了 GitHub 的 runner 上（0.5.0），开发用的服务器不再跑测试。
